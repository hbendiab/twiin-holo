Architecture Twiin

Twiin regarde un salarié faire une tâche une fois, la comprend, la fait valider, la rejoue dans une copie isolée, essaie cinq façons de la faire, puis propose la meilleure : l'accélérer avec des conseils, ou l'automatiser avec n8n et Holo. Cette page liste chaque technologie utilisée, à quelle étape, et pourquoi.

Version finale visée

Ce qu'on veut livrer

Le salarié n'installe et ne configure rien. Il se connecte avec le compte de son entreprise. Tout le calcul tourne dans le cloud, en Europe, dans des environnements jetables. Sur le poste, il ne reste qu'un petit capteur.

Ce qui change par rapport à aujourd'hui

  • Le serveur Twiin quitte le poste pour le cloud (UE).
  • Un conteneur jetable par tâche, réseau fermé sauf les API utiles.
  • n8n hébergé, un par entreprise.
  • Clés et mots de passe dans un coffre côté serveur, plus de fichier local.
  • Connexion des salariés par SSO via Supabase Auth.

Ce qui reste identique

  • Le parcours : audit, enregistrement, question, reco.
  • Les 5 essais : 3 « conseil », 2 « automatisation ».
  • Holo seulement là où il n'y a ni API ni page lisible.
  • Aucune automatisation ne prend l'écran du salarié.
  • Les captures restent sur le poste par défaut.

Limites connues

  • Sur Mac, l'autorisation d'enregistrer l'écran se donne une fois par utilisateur (règle d'Apple).
  • Un logiciel de bureau sans API garde un agent local.
  • L'interrupteur DISCOVERY est retiré au rendu final.

Le graphe de l'entreprise

Dans Supabase, tout est relié : un salarié fait des tâches, une tâche utilise des logiciels, chaque tâche a ses essais, une automatisation sert une ou plusieurs tâches. En version finale, Twiin montre ces liens comme un graphe vivant, dans la page Back et pour la DSI. Quand deux salariés font la même tâche, Twiin le voit, et une seule automatisation sert les deux.
